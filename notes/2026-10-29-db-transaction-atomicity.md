# 数据库事务与原子性写法

- 日期：2026-10-29
- 标签：Node.js、mysql2、数据库事务

## 流程（createItem 新增条目）

一次请求要写两张表，外加写入前的校验，全部在同一个事务里完成：

1. `getConnection()` 锁定一条连接
2. `beginTransaction()`
3. 校验标签归属（`SELECT ... WHERE user_id = ? AND id IN (?)`）
4. `INSERT INTO media_items`，拿数据库返回的 `insertId`
5. 批量 `INSERT INTO media_item_tags`
6. `commit()` 之后才返回响应
7. 出错 `rollback()`，`finally` 里 `release()`

## 为什么要采用原子性写法

- **两步写入，缺一不可**：主表写了、关联表没写（或反过来），就留下脏数据——有条目没标签，或有标签指向不存在的条目。原子性让操作「全做或全不做」，失败整体回滚到起点。
- **校验和写入之间有空窗**：外键只保证标签存在，不保证属于当前用户。查完归属再到插入之间，标签可能被删、被改归属。放进同一个事务，校验和写入看到的是同一份数据，空窗被堵上。
- **依赖前一步的结果**：关联表插入依赖主表的 `insertId`，两步必须同生共死，中间任何一步失败，先写的那步也不能留下。

## 保证原子性的四件事（缺一不可）

| 事情 | 不做的后果 |
|---|---|
| `getConnection()` 锁定连接 | `pool.query` 每次可能换连接，事务根本不成立 |
| `commit()` | 不提交，数据不会真正落库 |
| 出错时 `rollback()` | 失败的半截数据留在库里 |
| `finally` 里 `release()` | 连接被占干，服务几次请求后就卡死 |

## 什么时候需要原子性写法

- 一次请求写**多张表**（主表 + 关联表、订单 + 订单明细）
- 写入前有**校验查询**，校验结果必须对写入时刻仍然有效
- 步骤之间有**依赖顺序**（第二步用第一步的 `insertId`）
- 任何一步失败，需要**整体撤销**才能保证数据一致

## 什么时候不需要原子性写法

- **单条** INSERT / UPDATE / DELETE——一条语句本身就是原子的
- 只读查询
- 各步骤互不相关，失败后可以各自独立存在、单独重试
- 可以接受「事后补偿」的操作（写日志、发通知这类），失败单独处理即可，不值得开事务

## 补充：几个坑

- 不要在 `commit()` 之前返回响应
- `rollback()` 也要 `.catch(() => {})`，回滚失败不要盖掉原始错误
- 批量插入的 `VALUES ?` 数组展开只支持 `query`，不支持 `execute`
- 以数据库返回的 `insertId` 为准，不接受前端传来的 id
